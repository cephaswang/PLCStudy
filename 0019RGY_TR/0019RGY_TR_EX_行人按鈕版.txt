(*================================================================
實作題2：紅綠燈交通號誌控制（含行人按鈕中斷）－ ST（結構化文字）版
機型：三菱 FX5CPU / FX5U　開發軟體：GX Works3
基礎來源：0019RGY_TR.txt（v1.3，X0_TRIG改為一般繼電器電位判斷版）
版本：v1.4 － 新增「行人通過按鍵」中斷邏輯
================================================================*)

(*
VAR
X0          : BOOL;    // 啟動開關（維持型，X0=ON運轉／OFF停止）
X1          : BOOL;    // 【新增】行人通過按鍵（瞬時按鈕，按下=ON）
Y0          : BOOL;    // 綠燈輸出
Y1          : BOOL;    // 黃燈輸出
Y2          : BOOL;    // 紅燈輸出

M0          : BOOL;    // 綠燈階段旗標
M1          : BOOL;    // 黃燈階段旗標
M2          : BOOL;    // 紅燈階段旗標
M11         : BOOL;    // 【新增】行人按鍵請求鎖存旗標

TMR0        : TON;     // 綠燈計時 5.0秒
TMR1        : TON;     // 黃燈計時 2.0秒
TMR2        : TON;     // 紅燈計時 5.0秒

X0_TRIG     : BOOL;    // 開機首次啟動旗標（電位判斷，非上升緣偵測，同v1.3）
END_VAR
*)

(*----------------------------------------------------------------
需求說明與設計決策（請先閱讀，說明為何未「直接跳綠燈→紅燈」）：

原始需求：「在綠燈時，若行人按下按鍵，需等綠燈進行3.0秒，接受中斷，進入紅燈」

若真的做成「M0(綠燈)直接跳到M2(紅燈)」，會與現有的 M0/M2 互鎖寫法
(M0 靠 ANI M1 關閉、M2 靠 ANI M0 開啟) 產生互相等待的死結：
  - M0 那行要等「看到M2=ON」才會關閉，但M2還沒被驅動過，M2=0
  - M2 那行要等「看到M0=OFF」才會開啟，但M0還沒關閉，M0=1
兩邊互相卡住，本次掃描誰都動不了，行人請求永遠無法真正生效
（且就算硬用SET/RST強制切換，也會讓Y0綠燈與Y2紅燈在切換瞬間
同時被點亮，是實際路口不允許出現的危險狀態）。

因此本版改採用與原程式「T0驅動綠→黃」完全相同、已驗證可行的
機制：行人請求達成條件後，比照 T0 計時到的效果，直接「提前觸發
進入黃燈(M1)」，讓程式沿用原本 黃燈(2.0秒)→紅燈(5.0秒) 的既有
安全流程，而不是自創一條新的切換路徑。也就是說：
「行人按鍵 + 綠燈已滿3.0秒」＝「等同於T0提早跳停」，效果是提前
結束綠燈、按照原有正常流程進入黃燈、紅燈，符合實際路口在停止
車流前一定要有黃燈警示的安全做法。

若你確定要「跳過黃燈、綠燈瞬間直接變紅燈」，做法上可行但需要另外
用 SET/RST 搭配額外的一次性判斷式來避開上述死結，且會有短暫綠紅
同時亮的疑慮，故本版不採用，若仍需要此種做法我可以另外提供。
----------------------------------------------------------------*)

(* 0. X0_TRIG 起動旗標（沿用v1.3寫法，電位判斷、非上升緣偵測） *)
X0_TRIG := X0 AND NOT M0 AND NOT M1 AND NOT M2;

(* 0.5【新增】行人按鍵請求鎖存 M11
條件：綠燈期間(M0=ON)按下X1即鎖存為TRUE，不論當下綠燈是否已滿3.0秒，
      先記住「有人要過馬路」；鎖存後會一直保持ON(自保)，
      直到黃燈M1被觸發(代表請求已被接受、開始執行切燈)或X0停止運轉
      為止才清除，避免請求被漏掉，也避免同一次過馬路被重複觸發。 *)
M11 := (X1 AND M0) OR (M11 AND NOT M1 AND X0);

(* 1. 綠燈階段旗標 M0　－ 邏輯與v1.3完全相同，未修改 *)
M0 := (TMR2.Q OR M0 OR X0_TRIG) AND NOT M1 AND X0;

(* 2.【修改】黃燈階段旗標 M1
原條件：(T0完成 OR M1自保) AND 非紅燈 AND 運轉中
新增條件：OR (行人請求M11已鎖存 AND 綠燈已達3.0秒)
效果：只要「行人已按過鍵」且「綠燈跑滿3.0秒」，即使T0(5.0秒)還沒到，
      也會提前觸發進入黃燈，之後黃燈(2.0秒)、紅燈(5.0秒)流程不變。 *)
M1 := (TMR0.Q OR M1 OR (M11 AND TMR0.ET >= T#3S)) AND NOT M2 AND X0;

(* 3. 紅燈階段旗標 M2　－ 邏輯與v1.3完全相同，未修改 *)
M2 := (TMR1.Q OR M2) AND NOT M0 AND X0;

(* 4. 燈號輸出 *)
Y0 := M0;
Y1 := M1;
Y2 := M2;

(* 5. 計時器　－ 時間設定與v1.3完全相同，未修改 *)
TMR0(IN := M0, PT := T#5S);   // 綠燈 5.0秒
TMR1(IN := M1, PT := T#2S);   // 黃燈 2.0秒
TMR2(IN := M2, PT := T#5S);   // 紅燈 5.0秒

(*----------------------------------------------------------------
動作說明（新增行人按鍵後的完整流程）：

情境A：綠燈開始後第1.5秒，行人按下X1
  → M11在該掃描立即鎖存為TRUE(此時TMR0.ET=1.5S尚未達3.0S，暫不生效)
  → 綠燈繼續倒數，到達第3.0秒瞬間，M11 AND TMR0.ET>=3S 條件成立
  → M1提前導通(黃燈亮)，M11隨即因"NOT M1"不成立而自動清除鎖存
  → 之後黃燈跑滿2.0秒→ 自動轉紅燈5.0秒 → 循環繼續

情境B：綠燈開始後第4.0秒，行人才按下X1
  → 此時TMR0.ET已經是4.0S(已超過3.0S)，M11鎖存的同一掃描
    "M11 AND TMR0.ET>=3S"隨即成立，幾乎立即提前進入黃燈
    (只比原本5.0秒的自然切換提早約1秒)

情境C：綠燈全程都沒人按按鍵
  → M11維持FALSE，行為與v1.3原程式完全一致，5.0秒後正常轉黃燈

情境D：非綠燈期間(黃燈或紅燈)按下X1
  → "X1 AND M0"條件不成立(此時M0=0)，M11不會被鎖存，按鍵不生效，
    符合「只在綠燈期間才受理行人請求」的需求
================================================================*)
